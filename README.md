# weathercli Codespaces

GitHub Codespaces environments for the free-code tasks of a usability study that compares
[Nix](https://nixos.org) with [Nixty](https://www.npmjs.com/package/nixty-lib) (a TypeScript DSL
that generates `flake.nix`). Participants open the codespace from the survey, edit one file, test
it, and paste the whole file back into the survey. Nothing done in the codespace is recorded.

| Tool | Opens | Link |
|---|---|---|
| Nix | `nix/`, file `flake.nix` | <https://codespaces.new/DanielRasho/Thesis-survey?quickstart=1&devcontainer_path=.devcontainer/nix/devcontainer.json> |
| Nixty | `nixty/`, file `nixty.ts` | <https://codespaces.new/DanielRasho/Thesis-survey?quickstart=1&devcontainer_path=.devcontainer/nixty/devcontainer.json> |

`quickstart=1` resumes the participant's existing codespace instead of creating a second one.

## Rules

- **This repo is public.** Never commit task solutions, answer keys, or the starters of the later
  tasks: each tool's folder holds only the first task's starter. Participants paste the other
  starters from the survey. The answer key lives in this folder but is ignored by git (see
  [Checking the tasks](#checking-the-tasks)); never `git add -f` it.
- The participant READMEs (`nix/README.md`, `nixty/README.md`) are in Spanish and **parallel**:
  same sections, same length, same level of help. Extra help in one biases the comparison. No
  hints about the solutions.
- Both environments are identical except for the tool-specific parts. Keep the two
  `devcontainer.json` files in sync.

## Layout

```
.devcontainer/
  nix/devcontainer.json      # opens nix/
  nixty/devcontainer.json    # opens nixty/
  shared/on-create.sh        # warm-up, run by both (onCreateCommand)
nix/                         # flake.nix, flake.lock, weathercli.sh, README.md
nixty/                       # nixty.ts, flake.nix (generated), flake.lock, package*.json,
                             # tsconfig.json, weathercli.sh, README.md

# local only, ignored by git:
tasks/<tool>/PE{9,10,11}/    # starter + solution of every task (the answer key)
check.sh                     # builds them all against this repo
PLAN.md                      # implementation plan of this environment
```

- `weathercli.sh` is the same file in both folders, mode 755.
- `nixty/flake.nix` is generated by `nixty generate` and **committed**: Nix only sees files git
  tracks, so a participant's regenerated `flake.nix` is picked up without `git add`. After
  editing `nixty/nixty.ts`, run `npx nixty generate` and commit the result.
- `nixty/tsconfig.json` matches the settings `nixty generate` uses without one, so the editor and
  the type-check agree. VS Code keeps its bundled TypeScript (the workspace's is TypeScript 7);
  don't set `typescript.tsdk`.

## What is pinned

| What | Where |
|---|---|
| Base image `mcr.microsoft.com/devcontainers/typescript-node:5.2.1-22-trixie` (Node 22.23) | `devcontainer.json` |
| Nix feature `1.4.0` (digest in `devcontainer-lock.json`), Nix `2.34.4` | `devcontainer.json`, `devcontainer-lock.json` |
| nixpkgs, **the same commit in both folders** | `nix/flake.lock`, `nixty/flake.lock` |
| The `nixpkgs` flake registry entry, pinned to that commit; global registry off | `on-create.sh`, `flake-registry =` in `devcontainer.json` |
| nixd, nixfmt | from the nixpkgs commit in the folder's `flake.lock` (`on-create.sh`) |
| nixty-lib `0.1.1` (local and global) | `nixty/package.json`, `nixty/package-lock.json` |
| Extension `jnoortheen.nix-ide@0.5.13` | `devcontainer.json` |

To move nixpkgs to another commit, lock both folders to it and check they agree:

```sh
REV=<nixpkgs commit>
(cd nix   && nix flake lock --override-input nixpkgs github:NixOS/nixpkgs/$REV)
(cd nixty && nix flake lock --override-input nixpkgs github:NixOS/nixpkgs/$REV)
jq -r .nodes.nixpkgs.locked.rev nix/flake.lock nixty/flake.lock   # must print $REV twice
```

Why the registry pin: `nix develop` takes `bashInteractive` from the flake's `nixpkgs` input only
when that input is a flake. Nixty declares it with `flake = false`, so Nix falls back to the
`nixpkgs` registry entry, which would download the current nixpkgs-unstable the first time a
Nixty participant enters a dev shell. Pinned, both tools use the same commit and nothing is
downloaded.

The `devcontainer-lock.json` files are written by the devcontainer CLI; commit them when they change.

AI features are off by default (`chat.disableAIFeatures`, `github.copilot.enable`, and the Copilot
extensions excluded). A participant can turn them back on; the survey rules forbid them anyway.

## Warm-up and prebuilds

`.devcontainer/shared/on-create.sh` runs as `onCreateCommand`, so it runs inside the Codespaces
prebuild. It installs nixd and nixfmt, builds the package, and enters `nix develop` once, so the
Nix store already holds nixpkgs, stdenv, makeWrapper, curl, jq and bashInteractive. For Nixty it
also runs `npm ci`, installs the `nixty` CLI globally and builds with `nixty build`, which warms
the type-check. It fails if it leaves the tool's folder dirty.

Prebuilds are configured in the repo settings (Settings → Codespaces → Set up prebuild), **once
per devcontainer config**: branch `main`, trigger "On configuration change", one region (the
closest to the participants). They run on GitHub Actions and are billed to the repo owner.

## Testing locally

With Docker running:

```sh
npx @devcontainers/cli up --workspace-folder . --config .devcontainer/nix/devcontainer.json
npx @devcontainers/cli exec --workspace-folder . --config .devcontainer/nix/devcontainer.json \
  bash -lc 'nix build && ./result/bin/weathercli && nixd --version && git status --short'
```

Same with `.devcontainer/nixty/devcontainer.json` and `nixty build weathercli`. `on-create.sh`
fails if the tool's folder has uncommitted changes, so test from a fresh clone.

## Checking the tasks

`tasks/` holds the starter and the reference solution of every task for both tools. It is the
answer key used to grade the pasted answers, so it stays in this folder **ignored by git**, like
`check.sh` (which names what the solutions use) and `PLAN.md`. Keep a backup elsewhere: git
doesn't hold them.

After changing the tasks, the flakes, the lock files or `nixty-lib`, run (needs Nix and Node):

```sh
./check.sh                                         # this repo only
./check.sh --yaml <survey>/server/content/nix.yaml # also: the Nix starters equal the survey's code
```

For every tool × task × {starter, solution} it copies the tool's folder to a temporary git repo,
pastes the file in, builds it with the README's command and asserts the behaviour expected of that
variant, and that `flake.lock` is untouched. It also fails if the answer key is tracked or a tool
folder contains solution code.
